## Blocking chain

The table distinguishes JS scheduling from Expo native dispatch. There is **no single application-wide JS promise chain** serializing all keys in the current adapter. Chunks are submitted concurrently; manifest publication is serialized **per key**, recovering from earlier rejection with `.catch(() => {})`. Native encrypted SharedPreferences work still shares a backing file. A timing measured around a JS native promise includes dispatch, waiting, execution and delivery; it is not native execution time alone.

## Causal findings and correction

The original scheduler starts a second native generation for an identical active payload. A blocked fake-native reproducer produces **two chunk writes**, and both receipts remain pending. The correction joins the first generation's resolver list only when it is the **sole active generation** and there is **no pending payload**. After correction it produces one generation, and both receipts still await verified publication and the existing final read. It does not serialize differing active writes, drop mutations, alter owner data, or make queued work durable.

Failure/retry coverage verifies that both joined receipts reject, the previous committed value remains readable, retry succeeds, and an older identical active write cannot absorb a request across a newer pending payload. Existing delayed older-generation ordering test remains unchanged and passes.

**PERF-003 classification for the original native audit incident: Blocked from verification.** The stall is separately reproduced and causally traced **under controlled delayed durable-receipt conditions in the actual Focus component integration test**. A 150-second held receipt prevents the completion screen from appearing; settling that one promise immediately permits completion without changing the timer or network flush. Ten normal synthetic 10-second component sessions complete after the existing settle. Existing failed-write tests show truthful unsaved completion. **The original once-observed native >2.5-minute incident has not been reproduced or conclusively attributed. Ten native UI sessions and native fault-injected practice acceptance remain open.** This distinction is essential: a controlled reproducer identifies a real blocking path, not the provenance of a historical incident.

Native backlog has source-confirmed amplification: full retained owner collection for each ordinary write; chunk write + readback + publication + old-generation deletion + final committed reread; uncoalesced in-flight duplicates; direct unbatched auth/cache writes and retained account snapshots on the same native backing file. Expo SecureStore 15.0.8 calls synchronous SharedPreferences `commit()` for encrypted item publication. There is no evidence that the old 220-second window represents one isolated write service time or a single JS global queue. Its exact generation count/duplicate fraction cannot be reconstructed from the previous aggregate counters.

Re-examining the latest retained numeric `native-validation-guest-r2-progress.json` establishes **at least three overlapping vault generation writes**, each 393 chunks: 706,010 chars / 83.224s; 706,010 chars / 176.931s; 706,567 chars / 212.013s. The final adapter receipt is 220.091s, and the controller snapshot counts 1,198 native writes and 2,793 reads across adapter keys. The first two equal sizes do **not** prove byte equality. Starts inferred from `end - duration` overlap. This bounds the observed backlog and supports amplification; it does not recover native dispatcher/service timing or establish that every write was redundant.

Startup has several independently necessary gates. Source confirms an unbounded token/backend sync and awaited cached-profile writes before `authRestorationSettled`. Data hydration is not directly awaited by shell readiness. **The previous 35.9–75.4-second observations have insufficient per-dependency spans to assign their exact causal split.** The new retained-APK cold launch reproduces 66.517s app-ready, 10.234s vault hydration and an overlapping 82.087s durable receipt. It does not prove the write caused app-ready or certify usable Home. API/Auth emulator services were unavailable; the running host/emulator differs in surrounding load from the prior checkpoint. These are descriptive results, not a before/after claim.

## Scope and architecture recommendation

The adapter correction is a narrow duplicate-request correction, not a remedy for all RC-1 latency. Differing in-flight generations, whole-vault serialization, retained snapshots, readback and shared encrypted SharedPreferences amplification remain. Do not remove integrity verification, owner partitions, recovery copies or legacy data for speed. Do not remove Focus's durable barrier without a reviewed pending/failed/retry presentation and stable-ID lifecycle; that would be a separate product behavior change.

The next high-impact pass should **design and seek approval for** the proposed SQLCipher migration using the retained-collection/chunk amplification evidence. Do not begin implementation based on this checkpoint alone. Approval decisions: encrypted database dependency/runtime and key handling; schema/owner/recovery/guest-transfer contracts; transactional durable receipts and per-record writes; crash-safe import and legacy retention; rollback/rollout gates; physical Android/iOS acceptance; practice queue concurrency/stale-generation guards; approved pending-save/retry behavior; lifecycle/reconnect queue draining. Those are unresolved design/acceptance requirements, not permission to weaken the current data-safety guarantees.
