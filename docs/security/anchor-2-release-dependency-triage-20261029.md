# Anchor 2.0 dependency reachability triage — 2026-10-29

This is a bounded source and installed-package review, not a penetration test or a certification of a deployed binary. No production service was contacted, deployed, or changed. Recheck deferred findings by **2026-11-05 and before release**, owned by the release engineer. A package being installed does not establish exploitability; absence of an identified source path does not prove that every transitive SDK path is safe.

## Inputs and method

The supplied production-omit-dev audit snapshots were `%TEMP%/anchor-release-backend-audit-final.json` and `%TEMP%/anchor-release-mobile-audit.json`. At initial inspection they reported backend **4 critical / 14 high / 61 total** and mobile **3 critical / 16 high / 31 total**. These counts precede the additional body-parser and express-rate-limit patches below and must not be represented as a fresh post-patch audit. Package versions and parents were corroborated with `npm explain ... --omit=dev --json`, installed source, lockfiles and application imports.

The subsequent backend production-omit-dev audit after the narrow dependency patches reported **60 total findings: 4 critical, 12 high, 43 moderate and 1 low**. Remaining package-level findings retain the conditional dispositions below; the count is not a claim that those findings are exploitable or resolved.

`--omit=dev` still includes Expo/Metro/build utilities classified as production dependencies by their parent package. It is not a list of code necessarily included or executed in a store binary. No release bundle contents, actual ingress address representation, production proxy settings, certificate infrastructure or live third-party responses were verified here.

Threat boundaries inspected: anonymous HTTP bodies before authentication; authenticated JSON routed through Zod; IP-derived rate and guest-cost keys; outbound provider/RevenueCat/storage requests; native mobile networking and deep links; SDK protocol parsers; build-time project files and signing material.

## Material findings addressed locally

| Finding | Source and bounded evidence | Local disposition |
|---|---|---|
| IPv4-mapped clients share a rate/guest-budget bucket | Installed `express-rate-limit@8.2.1` mapped both `::ffff:192.0.2.1` and `::ffff:198.51.100.2` to `::/56`. This could deny unrelated users if ingress supplies mapped addresses. A regression failed on that version. | Patched to **8.2.2**, preserving per-client keys; regression passes. Actual production ingress behavior remains unverified. [Maintainer advisory](https://github.com/express-rate-limit/express-rate-limit/security/advisories/GHSA-46wh-pxpv-q5gq). |
| Compressed-request decoder error after body processing | `index.ts` uses JSON/urlencoded parsers before auth, with default decompression. `body-parser@1.20.4` is in the affected range. The maintainer reports an uncaught late decoder error; ordinary body size caps do not address that lifecycle. | Compatible patch to **1.20.9**. Two isolated child HTTP probes with small gzip/deflate frames and delayed trailing bytes remained healthy both before and after the patch; **those probes did not reproduce the published crash**. [Maintainer advisory](https://github.com/expressjs/body-parser/security/advisories/GHSA-27r3-jxmh-p828). |
| Zod issue amplification within the body byte limit | Installed `zod@3.25.76`: a 50,001-byte array of 10,000 nulls validated against `z.array(z.string()).max(2)` produced **10,001 issues**. Array maxima do not stop this version from validating every element. Anchor creation accepts `distilledLetters`, and route validators format every error. No out-of-memory test was attempted. | Added [body complexity guard](../../backend/src/api/middleware/bodyComplexity.ts) after parsers and before auth/routes: arrays and own object keys at most **1,024** each, **8,192 total nodes**, depth **32**. Iterative traversal rejects excessive structure with **413 / PAYLOAD_TOO_COMPLEX** before Zod. Raw buffers and primitives remain untouched; byte limits and existing schemas remain intact. [Advisory](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5). |
| Native image decoder exposure | Anchor and Vision workflows process generated/uploaded raster content and SVGs; this is a real decoder boundary. | Parent release work patched **Sharp 0.35.5** and verified native image operations. Two malformed hardcoded PNG test fixtures were replaced with valid generated PNGs, retaining the assertions. This does not certify every image codec/input. |

The complexity guard was checked against current endpoint shapes: examples include 3 Ask attachments, 4 Chart references, 6 onboarding answers, 12 waypoints and 20 mantra letters. No bulk legacy-vault array POST was found in the inspected auth/Anchor routes. Large image strings retain the existing byte and decoded-image limits; their character count is not interpreted as a collection size by the new guard.

## Evidence and remaining work

- [Request dependency regressions](../../backend/src/api/middleware/__tests__/requestAbuseSafety.test.ts): distinct mapped-IP keys failed before the rate-limit patch and passed afterward; bounded compressed HTTP probes did not crash before or after the body-parser patch.
- [Body complexity regressions](../../backend/src/api/middleware/__tests__/bodyComplexity.test.ts): ordinary nested requests, schema failures, raw buffers, 10,000-entry arrays, excessive object keys, total node count, depth and global registration order. At creation of this appendix, both focused suites passed **11/11** tests.
- Source registration: [backend entry point](../../backend/src/index.ts), including byte caps and numeric proxy trust. Image-fetch limits: [StorageService](../../backend/src/services/StorageService.ts). Current native networking: [apiClient](../../anchor/mobile/src/services/ApiClient.ts). Current manual URL handling: [chartDeepLinks](../../anchor/mobile/src/navigation/chartDeepLinks.ts).
- A current production-omit-dev audit must be retained after all lockfile changes. The tables document the inspected snapshot and disposition, not a claim of zero high/critical package findings.
- Remaining SDK/parser and build-tool findings require the listed compatible dependency remediation or explicit, time-bounded release acceptance. Binary and ingress verification remain open. This appendix does not approve shipping unresolved findings or replace the final release audit.
